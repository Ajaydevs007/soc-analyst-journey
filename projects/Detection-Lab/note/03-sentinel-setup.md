# 04 — Microsoft Sentinel Setup

## Objective

Connect the Windows Server Domain Controller and Windows 10 endpoint to Microsoft Sentinel so that Windows Security Events can be collected and queried for SOC detection.

---

The Sentinel environment was created inside:

```text
Resource Group: rg-detection-lab
Region: Central India

Log Analytics Workspace
Workspace: law-detection-lab-ci
Region: Central India

Microsoft Sentinel was enabled on the Log Analytics workspace.
Microsoft Sentinel
Microsoft Sentinel was enabled for:
Workspace: law-detection-lab-ci

The Windows Security Events solution was installed from the Microsoft Sentinel Content Hub.
The lab uses the Windows Security Events via AMA connector.
Windows Security Events collected through this connector are written to the:
SecurityEvent

table in Log Analytics. 
Azure Arc
Because the lab machines are VirtualBox virtual machines rather than Azure-native virtual machines, Azure Arc was used to make them available for Azure Monitor Agent management.
The following machines were connected to Azure Arc:
Machine	Role	Internal IP
SOC-LAB-DC	Domain Controller	10.10.10.10
SOC-LAB-WIN10	Windows Endpoint	10.10.10.20


Both machines were registered in:
rg-detection-lab

Microsoft requires Azure Arc for Windows machines that are not Azure VMs when using Azure Monitor Agent-based Sentinel connectors. 
Azure Monitor Agent
The Azure Monitor Agent (AMA) was installed on both Windows machines through the Azure Arc integration.
Extension:
AzureMonitorWindowsAgent

The agent extension reported:
Status: Succeeded

AMA Heartbeat Verification
Agent connectivity was verified using the following KQL query:
Heartbeat
| where Category == "Azure Monitor Agent"
| where TimeGenerated > ago(15m)
| project Computer, TimeGenerated, Category, OSType
| order by TimeGenerated desc

The query returned heartbeat records for:
SOC-LAB-DC
SOC-LAB-WIN10

This confirmed that both machines were communicating with Azure Monitor through the Azure Monitor Agent.
Data Collection Rule
A Data Collection Rule (DCR) was created to collect the Windows Security Events required for the detection lab.
DCR Name:
dcr-detection-lab-security-events

Associated Resources
The DCR was associated with:
SOC-LAB-DC
SOC-LAB-WIN10

Security Events Collected
The DCR was configured to collect:
Event ID 4624
Event ID 4625
Event ID 4771

These events provide the authentication telemetry required for the lab.
DCR XPath Configuration
The Windows Security Event collection filter used:
Security!*[System[(EventID=4624 or EventID=4625 or EventID=4771)]]

The XPath filter limits collection to the specific authentication events required by the lab instead of collecting the complete Security log.
Microsoft Sentinel supports custom Windows Security event collection through XPath-based filtering in Data Collection Rules. 
DCR Connection
The Microsoft Sentinel Windows Security Events via AMA connector reported the DCR connection as:
Connected

SecurityEvent Verification
After the DCR was configured, the collected events were queried from the SecurityEvent table.
Initial verification:
SecurityEvent
| take 10

Fresh authentication events were then confirmed using:
SecurityEvent
| where TimeGenerated > ago(15m)
| where EventID in (4625, 4771)
| project TimeGenerated, Computer, EventID, Account, Activity
| order by TimeGenerated desc

The query returned fresh events from the lab machines.
Detailed Event Verification
The following query was used to inspect authentication telemetry:
SecurityEvent
| where TimeGenerated > ago(30m)
| where EventID in (4625, 4771)
| project
    TimeGenerated,
    Computer,
    EventID,
    Account,
    TargetUserName,
    IpAddress,
    FailureReason,
    LogonType,
    Activity
| order by TimeGenerated desc

The collected data included:
- Event ID
- Computer
- Target account
- Source IP address
- Authentication activity
- Logon type
- Failure information


The SecurityEvent table contains Windows security event fields used for security monitoring and investigation. 
Event ID 4771 Verification
The Domain Controller generated Event ID 4771 during the controlled failed authentication test.
The event contained:
Target Account: user01
Source IP: 10.10.10.20
Service: krbtgt/SOC-LAB.LOCAL

This confirmed that the Kerberos authentication failure generated by the Active Directory environment was successfully collected by Microsoft Sentinel.

Result
The Microsoft Sentinel logging pipeline was successfully established.
The lab can now:
1. Generate Windows authentication activity.
2. Record the activity as Windows Security Events.
3. Collect selected events using Azure Monitor Agent.
4. Send the events through the configured DCR.
5. Store the events in Log Analytics.
6. Query the events using KQL.
7. Use the telemetry for Sentinel detection rules.
8. Generate Sentinel incidents from successful detections.
